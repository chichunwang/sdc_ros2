## 每一幀做什麼

```text
PLY ──► GPU 前處理（深度範圍、體素降採樣、孤立點）──────────────┐
影像 ─► SIFT 特徵 ─► GPU 描述子比對 ─► PnP（3D 來自上一幀點雲）─► 視覺初值
                                                                 ▼
                              GPU GICP／point-to-plane ICP 對局部子圖配準
                                                                 ▼
                    品質閘門 ──不通過──► 換初值＋放寬對應距離重試 ──仍不通過──► 沿用預測、標記失敗
                                                                 ▼
                    keyframe？──► 更新局部子圖 ──► 視覺閉環檢索 ──► 影像＋點雲驗證 ──► pose graph
```

### 1. 為什麼要用影像給配準初值

觀察：ICP／GICP 只會收斂到初值附近的局部最佳解。車輛轉彎時，等速模型預測的方向會錯，配準可能卡在錯的解。
做法（兩種模式，依資料自動選）：
- 車輛有移動時用 **Essential matrix**：RANSAC＋`recoverPose` 給旋轉與平移方向。它只用 2D 對應，不受 LoGeR 深度誤差影響（實測內點率約 95%）。平移長度 λ 再用上一幀的 3D 點估計：每個點給一個 λ 的最小平方解，取視差較大的一半再取中位數。
- 幾乎靜止（特徵位移中位數 < 2 px，Essential matrix 退化）時用 **PnP**：3D 來自上一幀點雲。
得到 `T_prev_cur` 後接到上一幀 pose：`T_init = T_w_prev · T_prev_cur`。

為什麼不全用 PnP：車輛移動時，LoGeR 約 5% 的深度誤差會讓重投影誤差超過 2 px，PnP 內點比例掉到 0.3。

### 1b. 視覺位姿不只當初值，也當先驗

觀察：只把視覺位姿當初值時，ICP 會把 pose 拉離它 0.15 m（中位數），單幀位移在 0.07–1.57 m 間亂跳（實際車速約 0.1–0.3 m／幀）。
做法：配準代價多加一項 `n·(w_t·|ξ_v|² + w_r·|ξ_ω|²)`，ξ 是目前 pose 相對視覺 pose 的左乘小量。權重由「點雲殘差標準差／視覺標準差」的平方除以有效獨立點數得到（`params.py` 的 `fusion`）。
**限制**：目前權重下視覺項佔主導（配準結果離視覺 pose 中位數僅 0.006 m），點雲主要透過閉環修正軌跡。這組權重是模型假設，沒有 GT 可校正。

### 2. 像素怎麼對到 3D 點

不假設 PLY 的點順序等於像素順序。實測每份 PLY 有 61,740 點，投影後是規則的 315×196 格點（約每 4.6 px 一點）。`PixelCloud` 在特徵點周圍四個格點之間對深度做雙線性內插，再沿特徵點的視線反投影；四個格點深度差超過 8%（深度不連續）就不給 3D。投影不成規則格點時退回最近點查表。
這個假設（點雲確實在該相機座標、內參正確）已用 `scripts/inspect_data.py` 驗證：投影位置的影像顏色與點顏色的平均絕對差是 0.0003–0.0006，隨機配對是 0.17–0.27。

### 3. GPU 配準的模型

source 點 `p`（相機座標）、target 是世界座標的局部子圖：`q = s·R·p + t`（`s` 預設固定為 1）。

- point-to-plane ICP：殘差 `e = nᵀ(q − m)`，`m` 是最近的 target 點、`n` 是它的法向。
- GICP：殘差 `r = q − m`，權重 `M = (C_m + s²·R·C_p·Rᵀ)⁻¹`，兩邊的共變異數都正則化成「一小片平面」`V·diag(ε,1,1)·Vᵀ`。
- 兩者都加 Cauchy 權重降低錯誤對應的影響，由粗到細分兩個階段（對應距離 1.0 m → 0.4 m）。
- 更新量 `δ = (v, ω, σ)`：`∂q/∂v = I`、`∂q/∂ω = −[q]×`、`∂q/∂σ = q − t`。

### 4. 品質閘門（全部通過才接受）

fitness、inlier RMSE、與初值的平移／旋轉差、資訊矩陣最小特徵值（幾何退化）、以及**配準出的相對旋轉與影像估計的相對旋轉是否一致**（旋轉不受點雲尺度影響，是獨立的檢查）。
不通過時依序重試；全部失敗就沿用預測 pose、標記 `tracking_failure`，運動狀態保留，不會讓 pose 跳回舊值。

### 5. 閉環

1. 檢索：目前 keyframe 的每個描述子在「夠久以前的 keyframe」描述子庫中找最相似者並投票（GPU 矩陣乘法）。
2. 影像驗證：Essential matrix 內點數、PnP 內點數。
3. 點雲驗證：以 PnP 結果為初值，把目前 keyframe 配準到候選 keyframe 附近的子圖；檢查 fitness、RMSE，以及**配準結果與影像估計是否一致**。
4. 全部通過才加入 pose graph（GTSAM，Huber 穩健核）。所有候選（含被拒絕的）都記在 `loop_candidates.csv`。

非 keyframe 的 pose：每幀相對前、後兩個 keyframe 各算一個修正後的候選，再在 SE(3) 上內插，因此經過 keyframe 時連續。

## 哪些真的在 GPU

| 運算 | 裝置 | 位置 |
| --- | --- | --- |
| 體素降採樣、深度／孤立點過濾 | CUDA（CuPy） | `gpu_cloud.py`、`preprocess.py` |
| 最近鄰搜尋、鄰域共變異數 | CUDA（自寫 RawKernel） | `gpu_cloud.py` |
| 法向／共變異數特徵分解、殘差、H 與 g 累加 | CUDA | `gpu_cloud.py`、`gpu_registration.py` |
| 描述子比對、閉環投票 | CUDA | `visual.py` |
| 6×6／7×7 線性解 | CPU | `gpu_registration.py` |
| **SIFT／ORB 特徵抽取** | **CPU**（pip 版 OpenCV 沒有 CUDA 模組） | `visual.py` |
| Essential／PnP RANSAC | CPU（資料量小） | `visual.py` |
| pose graph | CPU（GTSAM） | `pipeline.py` |
| SuperPoint＋LightGlue（選用） | CUDA（PyTorch） | `visual.py` |

沒有 CPU fallback：CuPy 匯入失敗或沒有 CUDA 裝置會直接報錯。驗證方法：`scripts/dev.sh gpu`（逐點比對 GPU 與 CPU 最近鄰、列出耗時與 GPU 記憶體使用）。

## 用 RViz 觀看執行過程

手動執行一律用 `scripts/dev.sh slam`：它會先開 RViz 視窗（若還沒開），再啟動 SLAM 並把狀態即時送到 RViz。

```bash
./scripts/dev.sh slam --track 01
```

```bash
./scripts/dev.sh slam --track 01 --frames 300
```

只開／重開 RViz 視窗用 `./scripts/dev.sh rviz`，關閉用 `./scripts/dev.sh rviz-stop`。關掉視窗後 SLAM 會印出警告並繼續跑完。

為什麼是兩個容器：SLAM 容器是 Python 3.9（官方 starter 指定），和 ROS 2 Humble 的 Python 3.10 不相容。所以 RViz 與 bridge（`scripts/rviz_bridge.py`）在另一個 `osrf/ros:humble-desktop` 容器 `midterm02_rviz`，SLAM 透過 TCP（`vslam/gslam/viz_stream.py`）把資料送過去。視覺化只讀狀態，不影響 pose；有開 RViz 的 run 會在 `test_info.json` 記 `rviz: true`。

RViz 畫面（設定檔 `config/vslam.rviz`）：

| 顯示項目 | 內容 |
| --- | --- |
| Camera (3D overlay) | 原始相機影像，疊上軌跡與 keyframe |
| Features and status | 特徵點（黃）、通過幾何驗證的匹配（綠線）、被剔除的匹配（紅線），左上角是幀號、追蹤狀態、內點數、fitness、RMSE、單幀位移 |
| Map (keyframes, RGB) | 所有 keyframe 依目前 pose 拼成的彩色地圖；閉環後會重新排列，牆面重影代表軌跡有誤 |
| Current frame cloud | 目前幀的點雲（紅） |
| Local submap | 配準目標（預設關閉，可勾選） |
| Path odometry／live／optimized | 灰＝純 odometry；黃＝執行中的 pose；藍＝結束時的最佳化結果 |
| Keyframes、Loop edges + camera frustum | keyframe 位姿（橘箭頭）、閉環邊（綠線）、相機視錐（黃） |
| TF | `map → world_cv → camera` |

SLAM 的世界座標是第一幀的相機軸（y 向下），bridge 用靜態 TF 轉成 RViz 的 z 向上，畫面才不會顛倒。
限制：黃色的即時軌跡不會在閉環後回頭修正舊的部分（keyframe 箭頭與地圖會）；完整的修正結果是結束時出現的藍線。

## 實測結果（Track01，2026-11-16）

沒有 ground truth，以下都是自我一致性指標，**不是精度**。「粗糙度」是相鄰三幀位置的二階差分（越大代表軌跡越鋸齒）。

300 幀短段，依修改順序：

| 版本 | 追蹤失敗 | 用到視覺初值的幀 | 粗糙度 中位數／p90 [m] | 路徑長 [m] |
| --- | --- | --- | --- | --- |
| 最近點查表＋PnP 初值（run `…160036`，200 幀） | 28／200 | 33 | — | — |
| 深度內插＋放寬等速閘門（`…160041`） | 0 | 210 | 0.304／0.734 | 79.3 |
| ＋視覺先驗融合（`…160042`） | 0 | 210 | 0.036／0.538 | 55.1 |
| ＋Essential 模式（`…160054`，含地面尺度） | 0 | 299 | 0.028／0.082 | 36.0 |

路徑長由 79 m 降到 36 m，是因為鋸齒被消除；Essential 與 PnP 兩種獨立的平移長度估計中位數比值為 0.994。

full（1314 幀）：

| 版本 | 閉環數 | 閉環配對處的 odometry 落差 中位數／最大 [m] |
| --- | --- | --- |
| 地面高度尺度正規化（`track01_full_2611160101`） | 20 | 3.92／7.08 |
| 不做尺度正規化（`track01_full_2611160106`、`…160111`，預設） | 22 | 2.21／3.68 |

**被否定的假說**：相機離地高度與影像估到的相鄰幀尺度比有正相關（r≈0.57，前 300 幀），所以我試了「尺度 = 參考高度／該幀高度」。full 上它讓 odometry 漂移變大，因此預設關閉（`scale.mode='none'`），程式保留供實驗（`E10a_ground_scale`）。可能原因：地面擬合受路面坡度與路緣影響；且靜止段裡兩種尺度指標的變化方向相反，表示 LoGeR 的誤差不是單一尺度係數。

可重現性：同參數兩次 full 的位置差最大 1.7×10⁻¹³ m（GPU 浮點加總順序），`result_1.csv` 的 SHA 因此不同，但對分數沒有影響。

其他觀察：
- 逐幀耗時中位數 176 ms，其中 SIFT 抽取（CPU）約 140 ms、GPU 配準 13.5 ms、GPU 比對 0.7 ms。
- 官方說路線約 247 m，我們的軌跡長 194 m；整體尺度不影響評分（Sim(3) 對齊）。
- 最佳化後的軌跡在起點附近（右側直線段）三圈沒有完全重合，且有幾處轉折，是目前最可疑的區域。

## 第一次 Kaggle 分數與後續診斷（2026-11-16）

| 提交 | run | Public ATE |
| --- | --- | --- |
| baseline（官方） | — | 0.955 |
| gslam 0.1.0（稀疏閉環、等向里程計不確定度） | `track01_full_2611160111` | **0.369** |
| 排行榜前 10 名 | — | 0.068–0.099 |

已優於 baseline，但與前段差五倍。以下診斷都沒有 ground truth，只能看跨圈的自我一致性。

**觀察 1：同一地點、不同圈的 LoGeR 深度可差 2–3 成。** 在閉環配對處比較兩圈匹配特徵的深度，比值在 1.00–1.34（log 標準差 0.08）。地面高度比與它的相關只有 0.28，所以「相機離地高度」不是這個尺度的可靠量測——LoGeR 的變形不是單一係數。

**觀察 2：里程計的局部長度跨圈不一致。** `scripts/segment_length_consistency.py` 比較同一段路（5–20 m）在兩圈的里程計路徑長；原始里程計的長度比對數標準差是 0.118。原因是平移長度來自上一幀的 LoGeR 深度。

**觀察 3：點雲配準會被尺度差帶偏。** 兩圈點雲尺度差 8%、景深約 8 m 時，配準位置會偏約 0.6 m；這解釋了舊版閉環處影像估計與點雲配準相差 0.2–0.9 m。

**觀察 4：每圈實際行車位置不同。** 閉環量到的橫向偏移中位數 0.38 m、起點處 1.8 m，所以「三圈完全疊合」本來就不是正確目標。

據此做的修改（gslam 0.2.0）：

| 修改 | 內容 |
| --- | --- |
| 密集跨圈閉環 | 每個 keyframe 都嘗試，可同時連到前兩圈；接受數 22 → 102 |
| 閉環位姿以影像為先驗 | 兩個 keyframe 相距約 1 m，深度誤差影響小；點雲配準放開尺度（不再被尺度差帶偏），只做驗證與微調 |
| 里程計邊沿行進方向放寬 | 橫向與旋轉 σ 維持很小，沿行進方向 σ = max(0.03 m, 10% × 位移) |
| 尺度圖 | 以相鄰幀深度比＋閉環尺度比解每幀 log 尺度（線性最小平方），先修正里程計長度再做 pose graph |

長度比對數標準差（越小越一致；錨點取自最新 run 的閉環）：

| 軌跡 | 數值 |
| --- | --- |
| 原始里程計 | 0.118 |
| 尺度圖修正後的里程計 | 0.104 |
| 0.1.0 最佳化後（Public 0.369） | 0.105 |
| ＋密集閉環、影像先驗閉環、沿行進方向放寬（`track01_full_2611160523`） | 0.087 |
| ＋尺度圖（`track01_full_2611160533`，目前預設） | 0.078 |

**限制，請務必留意**：這個指標用的錨點就是 pose graph 擬合的那些閉環，所以最佳化後的數值變小有一部分是必然的，不能當作精度證明；只有 Kaggle 分數能判定。尺度圖單獨的效果很小（0.118 → 0.104），代表里程計長度誤差大部分不是「整幀一個尺度係數」能解釋的。

其他已測、沒有幫助的方向：地面高度尺度正規化、追蹤時每幀多解尺度（尺度隨圈數漂移）、關閉視覺先驗融合（跨圈局部殘差 0.165 → 0.269，並出現追蹤失敗）、純幾何 GICP（0.313）。

**觀察（加 BA 之前）**：0.144 仍是前幾名（約 0.07）的兩倍。Public 只評 132 幀（約 25 m）且各自做 Sim(3) 對齊，所以這 0.14 m 是「局部形狀」的誤差。
里程計每一步的長度都來自 LoGeR 深度；pose graph 只能把誤差攤平，沒有新的量測可以把它修正。

**假說**：同一個特徵點被連續多幀（以及不同圈）看到時，它在每張影像的像素位置是不依賴 LoGeR 深度的量測，精度約 0.5 px。
把所有幀的位姿與特徵點 3D 位置一起解，讓它們同時解釋所有像素觀測，局部形狀就由影像決定，LoGeR 深度只剩下「提供初值、固定整體尺度」的角色。

**模型**（`vslam/gslam/bundle.py`，在 pose graph 之後執行）：

- 變數：每一幀的相機位姿、每條特徵軌跡的 3D 點。
- 殘差：重投影誤差（px，Huber）；相鄰幀里程計（刻意很鬆：旋轉 0.01 rad、平移 0.05 m）；閉環邊；第 0 幀固定。
- 軌跡：前端通過幾何驗證的相鄰幀匹配，加上已接受閉環的跨圈匹配，用連通元件連起來；同一軌跡在同一幀出現兩個特徵就整條丟掉。
- 初值：以 pose graph 的位姿做批次線性三角化；視差小於 1°、有觀測在相機後方、重投影誤差中位數超過 6 px 的軌跡不用。
- 求解：GTSAM LM（CPU 稀疏 Cholesky，先消去 3D 點）；第一輪後丟掉誤差超過 4 px 的觀測再解一次。

**實測**（`track01_full_2611161129`）：

| 項目 | 數值 |
| --- | --- |
| 原始軌跡 → 採用 | 126,130 → 33,708 條（73% 因視差不足被排除），329,796 個觀測，其中跨圈 7,304 條 |
| 重投影誤差中位數 | 1.40 px → 0.39 px |
| BA 耗時 | 75 秒（整個 full 約 7.4 分鐘） |
| 跨圈路段長度比的對數標準差 | 0.078 → 0.057（MAD 0.089 → 0.040） |
| 跨圈局部 RMSE（132 幀視窗） | 0.178 → 0.160 m |
| BA 前後軌跡的差（132 幀視窗、Sim(3) 對齊） | 0.11–0.29 m |

穩定性檢查（同一份輸入只改 BA 設定，與預設結果比較，132 幀視窗）：拿掉閉環邊 0.001 m、里程計放鬆到 0.15 m 為 0.005 m、視差門檻 0.5° 為 0.015 m、三輪 0.010 m；同設定重跑完全相同。
也就是說解幾乎完全由影像觀測決定，不靠里程計或閉環邊的權重。

**限制**：BA 把軌跡移動了 0.1–0.3 m，量級與目前的分數相當，但「更一致」不等於「更準」，要等 Kaggle 分數才能判定。重投影誤差是被最佳化的量，不能當精度證明。

## BA 加上更多影像配對（gslam 0.4.0，2026-11-16）

0.3.0 的 BA 只用「相鄰幀」和「已接受閉環的 102 對 keyframe」的特徵匹配。這一版多了三件事（都在 `params.py` 的 `bundle` 可開關）：

- **跨幀配對**（`skip_frames=3`）：每幀也和前第 2、3 幀比對並做 Essential RANSAC 驗證，軌跡較長、中間斷掉時接得回來。
- **依位姿的跨圈配對**（`revisit_links`）：pose graph 完成後，替每一幀找「別圈、相機相距 3 m 內、朝向相近」的幀，每一圈取最近的一幀來比對與驗證。跨圈影像對從 102 對增加到 1,656 對。
- **軌跡建立**（`resolve_conflicts`）：軌跡在同一幀出現兩個特徵時，原本整條丟掉；現在只對這些軌跡依「兩幀間隔由小到大」逐條匹配重新合併，會造成衝突的那條匹配才跳過。

**實測**（`track01_full_2611161431`，與 0.3.0 的 `track01_full_2611161129` 比較）：

所以**跨幀配對是變差的原因**，預設已關閉；跨圈配對在 Public 上與基本 BA 持平（差 0.001，在雜訊範圍內）。

**跨幀配對為什麼會變差（離線檢查，`outputs/cache/dev11.py`）**：用基本 BA 的位姿與 3D 點，檢查隔 2、3 幀的配對是否符合目前的幾何：

合併後的長軌跡把這些錯誤綁進 BA，局部尺度被拉偏。這是推論，與分數變差的方向一致，但沒有 ground truth 可以直接證明。

## 依特徵尺度給觀測權重（gslam 0.5.0，開發中）

**觀察**（`outputs/cache/dev12.py`，基本 BA 的 33,708 條軌跡）：SIFT 特徵的 size（被偵測到的尺度）越大，重投影誤差越大：

| size（px） | 佔比 | 誤差中位數 | 90% |
| --- | --- | --- | --- |
| < 2.5 | 2% | 0.23 | 0.58 |
| 3.5–5 | 16% | 0.32 | 0.86 |
| 8–15 | 26% | 0.50 | 1.38 |
| > 30 | 6% | 0.75 | 2.13 |

特徵的回應強度（response）則和誤差幾乎無關。原因：大尺度的特徵是在模糊、降解析度的影像層找到的，位置本來就比較不準。
目前 BA 對所有觀測一視同仁（1 px），等於讓定位差的大尺度特徵和精準的小尺度特徵有一樣的發言權。

**模型**：每個觀測的像素標準差 sigma = 1 px ×（size／6）^0.4，限制在 0.6–2.5 倍之間；第一輪後的剔除門檻也乘上同一個倍數。
0.4 次方來自上表誤差中位數對 size 的斜率，不是掃分數得來。開關在 `params.py` 的 `bundle.size_weight`，實驗名稱 `E16_size_weight`。

**結果**：full `track01_full_2611161541`，與基本 BA 比，軌跡在 132 幀視窗內差 0.015 m（中位數）、最大 0.028 m。
**Kaggle Public 0.092（使用者回報），比基本 BA 的 0.085 差**，所以預設維持關閉。

可能的原因（推論，未證實）：加權後大尺度特徵的發言權變小，而大尺度特徵多半是遠處或大面積的結構，對「整段路的形狀」反而比較有約束力；
小尺度特徵定位準，但多集中在近處，對局部尺度的約束較弱。重投影誤差較小，不代表軌跡較準。

**一個重要的觀察**：軌跡只差 1.5 cm，Public 卻差 0.007。
跨圈配對（差 4.9 cm → 0.001）、尺度加權（差 1.5 cm → 0.007）兩個例子說明：Public 只有 132 幀，對細小的形狀差異很敏感，而且和「軌跡改變多少」沒有單調關係。
所以 0.01 以內的分數差，不能當成方法好壞的可靠證據。

## 投影引導補觀測（`E17_guided`，2026-11-16）

**觀察**：跨幀配對讓分數變差，原因是 Essential matrix 的 RANSAC 只檢查點到對極線的距離，擋不住沿線方向的錯配。

**做法**（`bundle.guided_observations`）：BA 解完後，把「附近的幀」（相機相距 5 m 內、光軸夾角 30° 內，含其他圈經過同地點的幀）看到的 3D 點投影到每一幀，
只在投影位置 3 px 內找特徵，描述子相似度 ≥ 0.85 且明顯優於第二名才接受；已屬於其他軌跡的特徵不動。加入後再解一次 BA。
驗證的是完整的 3D 位置，所以沿對極線的錯配會被擋掉。也就是用後面的幀回頭補強前面的幀（不限時間順序）。

**結果**（full `track01_full_2611161550`）：補上 230,555 個觀測（跨圈 97,954 個），跨圈軌跡 7,304 → 19,909 條；
重投影誤差中位數 0.39 → 0.50 px（新觀測多為跨圈，本來就較難對準）。與基本 BA 的軌跡差：132 幀視窗中位數 0.021 m、最大 0.039 m。

**Kaggle Public 0.092（使用者回報），比基本 BA 的 0.085 差**，預設維持關閉。

## LoGeR 深度約束的 BA（`E18_depth`，gslam 0.6.0，2026-11-16）

**觀察**（`outputs/cache/dev16_depth.py`，基本 BA 的軌跡 vs 每個特徵在 LoGeR 點雲的深度）：

| 量測 | 數值 | 意義 |
| --- | --- | --- |
| 同一幀內，扣掉該幀整體尺度後的相對深度誤差 | MAD 0.087（3–10 m 只有 0.054–0.060） | 單張 LoGeR 的「相對遠近」相當準 |
| 每幀整體尺度偏差 s_i（log） | 標準差 0.074 | 整張的尺度會飄 |
| 相鄰幀 s_i 的變化 | 0.018；扣掉 11 幀移動中位數只剩 0.012 | 飄得很慢、很平滑 |
| 同一地點不同圈的 s_i 差 | 0.086 | 不同圈不能共用同一個尺度 |

單目 BA 的弱點是「沿行進方向的局部尺度」（IMU 檢查已確認轉角沒問題）。LoGeR 正好在這方面有資訊，只是不能直接當公尺用。

**模型**：每個有 LoGeR 深度的觀測加一個距離因子：

- 相機中心到 3D 點的距離 ≈ exp(s_i) × LoGeR 深度沿像素視線換算的距離。
- s_i 是每幀未知的 LoGeR 尺度偏差，相鄰幀平滑：s_i − s_{i−1} ~ N(0, 0.02)（實測 0.018）。
- 距離誤差 = 0.10 × 距離（實測同幀相對深度誤差 0.087），Huber。
- 交替求解：先固定 BA 解 s（三對角線性系統、IRLS），再固定 s 解 BA（GTSAM `RangeFactor3D`）；共 3 次。兩步優化同一個目標函數，所以會收斂。

這樣只用到 LoGeR 準的部分（同幀相對深度、短時間內的尺度），不會把各圈硬拉成同一個尺度。參數在 `params.py` 的 `bundle.depth`。

**離線結果**（與基本 BA 比，132 幀視窗）：

| 版本 | 與基本 BA 的差（中位數／最大） | 重投影誤差中位數 |
| --- | --- | --- |
| σ_d = 0.10（`E18_depth`） | 0.123／0.255 m | 0.52 px |
| σ_d = 0.30（權重約 1/9） | 0.081／0.158 m | 0.42 px |

**full**：`track01_full_2611161614`，與基本 BA 的差 0.122／0.253 m，與離線結果一致；Kaggle 分數見本節末。

兩個權重都往同一個方向移動，代表 LoGeR 深度給的是一致的拉力而不是雜訊；它也不是退回 pose graph（離 pose graph 0.134 m）。
移動量比先前所有 BA 變體（0.02–0.05 m）大得多，所以 Kaggle 分數可能明顯變好或明顯變差。
限制：同一幀的 LoGeR 誤差彼此相關（例如深度越遠偏差越大），把每個觀測當獨立量測可能高估了它的可信度。

**full 結果**（`track01_full_2611161614`）：BA 交替 3 輪，重投影誤差中位數 0.53 → 0.51 px，每輪約 30 萬個深度因子，每幀 log 尺度標準差 0.085；BA 共 116 s。
與離線 `dba_p1.csv` 的差：132 幀視窗中位數 0.002 m，實作與離線一致。

**Kaggle Public 0.087（使用者回報），與基本 BA 的 0.085 在雜訊範圍內。** 預設維持基本 BA。

## IMU 加速度計檢查局部尺度（離線檢查，`outputs/cache/dev19_imu_accel.py`，2026-11-16）

**為什麼需要**：E18 與基本 BA 爭的是「每段路實際多長」。影像量不出公尺，跨圈診斷又看不到三圈一起的變形，而 Track01 的 IMU 加速度計是唯一公制、與影像無關的量測。

**為什麼不積分成距離**：位置要積分兩次，偏差和重力洩漏會累積。這裡只積分一次，比較 2 秒內的速度變化，誤差小很多。

**模型**（世界座標沿用軌跡自己的座標）：

- 真實加速度 a(t) = R_wc(t)·(f(t) − b) + g。f 是加速度計讀數（用 `R_cam_imu` 轉到相機座標），b 是常數偏差，g 是重力向量；R_wc 用軌跡自己的旋轉（陀螺儀檢查已確認轉角正確）。
- 軌跡上第 k 幀的平均速度 v̄_k = (p_{k+5} − p_{k−5}) / 1 s，等於速度在這 1 秒內的平均，所以 IMU 這邊對積分出來的速度取同一段的平均，兩邊是同一個量。
- 相隔 2 秒的兩個平均速度相減，未知的初速就消掉：λ·Δv̄_軌跡 − ΔQ·r + ΔB·b − Δt·g = ΔF_IMU，對整體尺度 λ、偏差 b、重力 g、槓桿臂 r 都是線性的，一次最小平方解完。
- **槓桿臂**：IMU 和相機不在同一點，轉彎時兩點的速度不同（0.2 rad/s × 2.8 m ≈ 0.6 m/s）。不估它時殘差有 0.34 m/s，估了降到 0.13 m/s。車幾乎只繞垂直軸轉，垂直分量量不到，所以只估水平兩軸。
- 指標：擬合後的水平殘差 RMS（m/s），越小代表軌跡各段的長度越符合 IMU。

**物理檢查**：
- 所有 BA 版本估出的槓桿臂都是「相機在 IMU 前方約 2.8 m、橫向約 0」，符合 IMU 在車中段、相機在前擋的配置。
- 擬合出的 |g| 為 9.3–10.2 m/s²。
- 時間差在 ±0.1 s 內改變，結果幾乎不變。

**結果**（全部 1314 幀，642 組速度變化，訊號 RMS 1.37 m/s）：

- **差異完全在步長**，與旋轉無關：兩版旋轉互換後，殘差幾乎不變。
- **E18 的步長變化並不比隨機擾動好**，落在隨機分佈的最差一端。
- **呈現劑量反應**：深度因子權重越大，殘差越大（0.133 → 0.156 → 0.186），在 1–6 秒的各種窗長下都成立。
- **指標有足夠的分辨力**：同樣大小的隨機擾動，每次都讓殘差增加約 0.04 m/s。

**結論**：E18 依 LoGeR 深度重新分配的局部長度，和獨立的 IMU 加速度不一致。所以 Public 雖然持平（0.087／0.085），仍不採用 E18，預設維持基本 BA；σ_d = 0.3 的弱權重版也不必再試。
推論的原因：LoGeR 的深度誤差在同一幀、甚至相鄰幾幀之間是相關的（例如隨場景遠近改變），「每幀一個尺度 s_i＋獨立相對誤差」的模型不足以描述它。

**限制**：
- 這是自我一致性檢查，不是 GT。
- 在 BA 家族內部，殘差差異（0.132–0.148）和 Public 分數沒有明顯對應，只能分辨較大的差別，例如有沒有 BA、有沒有深度因子。
- 若之後把 IMU 加速度直接加進最佳化，這個指標就不能再當獨立驗證（會循環），要另外保留一部分資料或改用其他檢查。

## IMU 平均速度變化因子加進 BA（`E19_imu`，gslam 0.7.0，離線，2026-11-16）

**假說**：上一節顯示 IMU 加速度能分辨各段路的長度對不對；如果基本 BA 剩下的局部尺度誤差可以靠 IMU 修正，把同一個量測直接當成 BA 的因子，軌跡應該更準。

**模型**（`vslam/gslam/imu.py` 的 `velocity_factors`，`bundle.run` 的 `imu_windows`）：

- 量測：相鄰、不重疊的兩個 1 秒窗的平均速度差 v̄₂ − v̄₁，每段 IMU 資料只用一次。全程 130 個因子。
- 殘差只與三個位置有關，對旋轉的導數為 0；旋轉已由影像決定，且與陀螺儀吻合。
- λ、加速度計偏差、重力、槓桿臂：每次求解前依目前軌跡重新擬合，然後固定。這和 E18 一樣是交替求解。
- 第 1 次求解是一般 BA，第 2、3 次加上 IMU 因子。
- **雜訊**：取第一次擬合的垂直殘差（每軸），實測 0.017–0.022 m/s，Huber。路面近似平面，軌跡在垂直方向幾乎沒有誤差，所以垂直殘差可視為 IMU 雜訊的估計。
  這其實是**下限**：水平方向還有傾角誤差造成的重力洩漏（0.1° 就約 0.017 m/s²）和槓桿臂模型誤差，這兩項都不會出現在垂直方向。
- 合成檢查（`tests/test_imu.py`）：還原整體尺度與槓桿臂、偵測 8% 的局部拉伸、數值檢查 Jacobian；合成測試也抓到並修正了一個速度差符號錯誤。

**驗證設計**（避免「用 IMU 最佳化、再用 IMU 評分」的循環）：
- 把時間切成每 200 幀一塊，因子只放在偶數塊（`holdout_block_frames=200`），奇數塊的 IMU 資料完全不進最佳化，只用來檢查。
- 各圈經過同一路段的時間落在不同的塊，所以如果 IMU 真的修正了路線形狀，效果會透過跨圈共用的 3D 點傳到奇數塊。

**離線結果**（`outputs/cache/dev20_imuba.py`，用 `track01_full_2611161129` 的 BA 輸入走完整的 `bundle.run`）：

| --- | --- | --- |

| 只放偶數塊，σ 用實測值（0.017 m/s），Huber | 0.1091／0.1234 | 0.002／0.007 m |

**解讀**：
- 以有依據的權重加入時，軌跡只移動約 4 mm，影響遠小於 Public 能分辨的程度（1–5 cm 的變化就會讓分數在 0.01 內亂跳）。
- 即使把權重加到不合理的強度，讓偶數塊被強制貼近 IMU，保留的奇數塊也只改善 4%。也就是說，基本 BA 剩下的 IMU 殘差大部分不是「軌跡可以被修正的誤差」，而是 IMU 模型本身的誤差，例如傾角洩漏、槓桿臂與時間同步。
- 所以影像 BA 決定的局部長度已經和 IMU 一致到 IMU 能分辨的程度。IMU 的價值在於當**獨立檢查**（例如判斷 E18 不可採），而不是當約束。

**決定**：`E19_imu` 保留在程式中（預設關閉，Track02 沒有 IMU 時自動略過），**不跑 full、不提交**：預期結果和 0.085 的版本幾乎相同，重複提交沒有資訊量。

## 其他已排除的誤差來源（離線檢查，`outputs/cache/dev21_resid.py`，2026-11-16）

## 尺度會不會隨場景改變？（離線檢查，2026-11-16）

| 量測 | 結果 |
| --- | --- |
| 每幀尺度 s_i 的變動 | 標準差 6.8%，範圍 −19%～+21%；相鄰幀只差 2%，變化平滑 |
| 和「看到多遠」的相關（Spearman） | 景深中位數 r = −0.33、遠點比例 r = −0.39：開闊處 LoGeR 把深度估得偏大 |
| 依景深分四組的 s_i | 近景 +2.6% → 遠景 −1.6%（約 4% 差距） |
| 同一幀內遠近比例 | 3–20 m 幾乎無偏；小於 3 m 與 20–40 m 各偏約 5% |
| 同一地點、不同圈 | 差的標準差 5.1%，**平均 +6.0%**：後面的圈系統性偏移 |

所以 LoGeR 的尺度一部分隨場景變（景深），一部分隨時間漂移（同一地點不同圈差 6%）。
這解釋了為什麼地面高度正規化（E10a）、尺度圖、LoGeR 深度因子（E18）都沒有幫助：它們都假設 LoGeR 的尺度能用簡單的模型修正。

| --- | --- | --- |
| 純里程計（尺度來自 LoGeR） | 0.79–1.21（最後一段 2.36） | 0.44 |
| pose graph，無 BA（Public 0.144） | 0.87–1.10（最後一段 1.73） | 0.25 |

最後一段（第 1200 幀起）車幾乎靜止，IMU 訊號太弱，不可信。

## 更強的單張影像深度模型能否取代 LoGeR？（離線評估，2026-11-16）

**問題**：使用者提議用更強的深度模型，從原始影像重新產生稠密深度圖，取代或補強 LoGeR 點雲。

**為什麼要先量**：最終軌跡由 BA 用影像幾何決定，不使用 LoGeR 的深度或尺度。LoGeR 只用在前端初值與閉環驗證，而 BA 對初值不敏感。
所以深度模型只有在「比 LoGeR 準很多」時，才可能當 BA 的約束（E18 的方式）帶來改善。

**做法**（`outputs/cache/dev38_depth_models.py`、`dev35_scale_scene.py`）：
- 對全部 1314 幀推論，在每個特徵點取模型深度。
- 和自校正 BA 的三角化深度比較（只用視差 ≥2°、三角化誤差 <2 px 的點）。
- 環境：`docker/depth/Dockerfile`。

| 指標 | LoGeR（官方提供） | MoGe-2（MIT，給定水平視角） | Depth Anything V2 Metric Outdoor Large |
| --- | --- | --- | --- |
| 同一幀內相對深度誤差（扣掉每幀尺度後的穩健標準差） | **6.1%** | 6.8% | 9.4% |
| 每幀尺度浮動 | **6.8%** | 8.9% | 18.1% |
| 相鄰幀尺度變化 | **2.0%** | 10.7% | 8.6% |
| 同一地點不同圈的尺度差 | 5.1% | **4.3%** | 17.5% |
| 不同圈的系統性偏移 | +6.0% | **−0.5%** | +2.8% |
| 推論時間（1314 幀） | — | 59 s | 100 s |

**解讀**：
- **Depth Anything V2 Metric Outdoor 明顯較差**：它以虛擬 KITTI 的車道場景訓練，不適合這種近距離建築多的校園。
- **MoGe-2 與 LoGeR 互補，但都沒有更準**：MoGe-2 是單張影像模型，沒有隨時間累積的漂移，但逐幀很雜；LoGeR 是影片模型，短期平滑，但會隨時間漂移。
- **關鍵指標沒有改善**：同幀相對深度誤差兩者都約 6%。E18 已經顯示 6% 等級的深度當 BA 約束會讓軌跡與 IMU 更不一致。
- **都不如 BA 本身**：BA 的局部尺度起伏約 ±3–5%（IMU 分段檢查），比兩個深度模型的逐幀尺度都穩。

**決定**：不以單張影像深度模型取代或補強 LoGeR。MASt3R-SLAM（從影像直接預測稠密點圖的完整 SLAM）另外當作第三個獨立估計器測試。

## MASt3R-SLAM：第三個獨立估計器（2026-11-16）

**做法**：
- 環境：`docker/mast3r/Dockerfile`。MASt3R-SLAM commit e6f4e3d（CC BY-NC-SA 4.0），MASt3R 權重來自 naver。
- 為了在 torch 2.7 與 Blackwell（sm_120）上編譯，做了三處相容性修改：改用 `scalar_type()`、改用 `norm()`、強制編譯 CUDA 後端。都只是改 API 呼叫，不影響演算法。
- 執行入口 `scripts/run_mast3r.py`：演算法與參數維持官方設定，後端在主程序內逐 keyframe 執行（等同官方 single_thread 模式）。
- 官方只輸出 keyframe；這裡記下每幀相對其參考 keyframe 的 Sim(3)，最後接到最佳化後的 keyframe，得到每一幀的位姿。
- M1 用給定的針孔內參；M2 用自校正的主點與畸變（MASt3R-SLAM 自己校正影像）。1314 幀約 3 分鐘，143–149 個 keyframe，沒有觸發重定位。

**結果**（換算成相同單位，132 幀視窗中位數）：

| 比較 | 差 |
| --- | --- |
| M1（原內參）vs 基本 BA | 5.7 cm |
| **M1（原內參）vs E21（已校正）** | **3.1 cm** |
| M2 vs E21／M2 vs D2／D2 vs E21 | 3.2／約 3／2.9 cm |
| IMU 一致性 M1／M2 | 0.174／0.177（其他系統 0.11–0.13） |

**解讀**：
- **又一個支持自校正的獨立證據**：MASt3R 用學到的 3D 幾何，對內參誤差比較不敏感。即使沒有給它我們的校正，它也比較接近校正後的 E21，而不是基本 BA。
- 三個原理不同的系統（稀疏特徵 BA、稠密光流 DROID、3D 基礎模型 MASt3R）在校正後彼此都只差約 3 cm。
- MASt3R 本身的 IMU 一致性明顯較差，局部尺度的起伏也較大（每 150 幀 λ 標準差 0.082，其他系統約 0.05），所以只當成對照組。

## 跨圈點雲疊合：RViz 看到的牆面重影（`E26_selfcalib_cloud_overlap`，gslam 0.10.0，2026-11-16）

**觀察**：RViz 地圖上同一面牆在不同圈出現好幾條平行線，點雲沒有疊合。想法（使用者）：把「各圈點雲疊合程度」當成配準／最佳化的依據。

**先釐清畫面**：RViz 的地圖原本是用 pose graph 的 keyframe 位姿拼的，不是最終 BA 的輸出（`run_slam.py` 在收尾時送的是 `slam.keyframes` 的 T）。0.10.0 起改成用最終位姿重排地圖，畫面上看到的疊合就代表提交的軌跡。

**用最終軌跡量（`outputs/cache/dev39_overlap.py`，E21，89 個查詢幀）**：第 2、3 圈每 10 幀取一幀，把它的 LoGeR 點雲配準到較早一圈附近的點雲（用 E21 位姿拼成子圖），看配準要把它移多少：

| | 疊合前 fitness／RMSE | 配準要求的修正量（中位數） | 轉角 |
| --- | --- | --- | --- |
| 跨圈 | 0.77／0.191 | 0.46（橫向 0.20、前後 0.39） | 0.94° |
| 同圈對照（前後 4–24 幀） | 0.99／0.143 | 0.13 | 0.27° |

跨圈確實沒疊好（約 0.5 m），比同圈的點雲雜訊底線大很多。

**是位姿錯，還是點雲（LoGeR 深度）錯？（`outputs/cache/dev40_epipolar_check.py`）**：影像的 Essential matrix 和深度無關，給出兩幀之間的相對旋轉與平移「方向」。對同樣的跨圈配對（基線 > 0.5 的 32 對）：

| | 和影像平移方向的夾角（中位數） |
| --- | --- |
| E21 的 BA 位姿 | 3.5° |
| 照點雲疊合修正後 | 24.2° |

32 對裡 **0 對**在修正後更接近影像方向；BA 和影像的相對旋轉差中位數 0.43°。修正量又以前後方向（相機看出去的深度方向）為主。

**結論**：跨圈點雲沒疊合主要是 LoGeR 深度造成的：從不同位置、距離看同一面牆，深度誤差不同（同一幀內的相對深度誤差約 6%，10 m 的牆就差 0.6 m）。最終軌跡本身和影像幾何一致。所以「把點雲拉到疊合」會把位姿拉離影像給的幾何，**預期會變差**。

**仍照想法做成獨立版本 E26，當作驗證**：E21 的 BA 解完後，後面幾圈的每個 keyframe 點雲從 BA 位姿出發，配準到較早一圈的子圖（放開尺度，吸收 LoGeR 每幀尺度浮動）。通過品質閘門（fitness ≥ 0.6、RMSE ≤ 0.25、幾何不退化、修正 ≤ 2）的結果當成相對位姿邊（旋轉 0.5°、平移 0.15，Huber），再解一次 BA。每個候選記在 `debug/cloud_overlap.csv`。

## 還能改進什麼？（2026-11-17 盤點）

**三圈一致性分不出系統**（`outputs/cache/dev39_lapcmp.py`）：基本 BA、E21、E22、D1、D2、M1、融合，先 Sim(3) 對齊到 E21，再用 E21 的 82 個閉環錨點量，local RMSE 中位數都在 0.156–0.161、global 都在 0.560–0.566。這個指標的下限主要來自每圈實際行車路線不同，分不出這些系統的好壞。

**相機時間戳與 IMU 時鐘的時間差**（`outputs/cache/dev40_time_offset.py`，陀螺儀角速度 vs 軌跡角速度，1 ms 掃描＋拋物線內插）：

| --- | --- | --- |
| E21 | −15.7 ms | −14.4／−15.0／−18.5 |
| D2 | −13.0 ms | −13.1／−12.6／−13.7 |

- 假說：真值由 LiDAR（與 IMU 同一個 bag 時鐘）在影像時間戳上取值。如果成立，所有純視覺系統都報了「早 14 ms」的位置，這是三個系統彼此比較時看不出來的共同誤差。
- 量級：車速中位數約 2 m/s。改報到時間戳當下（p(t − δ)）後，位置在 132 幀視窗裡只差約 0.6–0.8 cm，全域約 1.5–1.8 cm。比 Public 的雜訊小，只能當成順手的修正，不是大突破。
- 限制：「真值在影像時間戳上取值、與 IMU 同一個時鐘」是假設，沒有真值無法確認。

## 已知風險

- 尺度估計（`estimate_scale`）的可觀測性：合成測試發現只有單側平面（一面地、一面側牆、一面前牆）時，尺度變化可被平移完全補償，配準會收斂到錯的尺度；兩側都有面才定得出尺度。真實街景是否足夠要用資料確認，所以預設關閉。
- 品質閘門、融合權重與閉環門檻都沒有 GT 可校正；目前只確認 Track01 上零追蹤失敗與三圈大致疊合。
- 資料包不含 `image_slam_starter/`，`data/` 的結構是手動放成 `data/data_VSLAM-T1/Track1/data/`；下載的 zip 留在 `data/_download/`。
- 學習式特徵（SuperPoint／ALIKED＋LightGlue）與其他公開預訓練模型：官方規則明確允許，使用者 2026-11-16 決定可直接納入正式結果（SuperPoint 權重為 Magic Leap 非商業研究授權、LightGlue 為 Apache-2.0，報告須註明）；starter README 另有「不得用完整 SLAM／SfM 系統產生提交」的規定，本程式是自寫流程，不屬於該類。

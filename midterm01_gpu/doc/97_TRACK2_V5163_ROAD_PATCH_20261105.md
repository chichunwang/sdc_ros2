## 觀察：影像速度缺少平面假設的支持

v5.16.2 第 616 幀額外融合 `5.237764 m/s` 影像速度，該筆更新前 sensor prior 為 `7.799148 m/s`。影像更新即時改變位置約 `0.234 m`，後續數幀 map 可觀測模式 rank 為 0，無法提供有效位置修正。不能將兩個速度中的任何一個直接視為真值。

同樣影像與特徵，使用自由 PnP（3D／2D 對應求相機運動）、固定 gyro 旋轉與聯合 solver，仍得到約 `5.24–5.38 m/s`。換 solver 沒解決分歧，因此沒有套用此研究改動。

## 實作：整個光流視窗需要路面支持

LK（Lucas–Kanade，局部視窗光流）以 `21×21` 像素追蹤。先將過去已驗證的路面 mask 按同一視窗侵蝕，再選角點。設路面 mask 為 \(M\)，視窗偏移為 \(W\)，可用中心為：

\[
M_{\mathrm{supported}}(u)=\bigwedge_{\delta\in W}M(u+\delta).
\]

圖外視為不支持。後續光流、深度、40 點最低支持量、PnP 與統計門檻保持原設定；全畫面靜止檢測不變。保留 **40 m** 配準範圍，只使用已到達影像、gyro 與過去已驗證尺度，不讀未來資料、不回修舊 pose。

這是必要支持條件，不保證粗金字塔視窗、遮擋或物體語意也正確。mask 自身仍可能誤判。直接位置是 [`image_speed.py`](../track2/image_speed.py) 的 `LK_WINDOW`、`road_patch_mask()`、`CausalGroundSpeed._ground_observation()`；總開關為 [`parameters.py`](../track2/parameters.py) 的 `V5163_ENABLED`。歷史 v5.16.3 的 V5161／2／3 都啟用，後續研究版本的實際值請看其凍結快照。

## 為什麼本機看起來改善，正式卻退步

按原到達順序、各版自己的實際影像與前幀高度重播感測器，v5.16.2／3 的 prior 逐值誤差均為 0。下表是融合前對下一筆 GNSS 的預測，共 473 筆；GNSS 本身是算法輸入，不能視為 pose 真值或 Kaggle 誤差。

| 版本 | XY forecast RMSE（m） | 左向（m） | 前向（m） |
| --- | ---: | ---: | ---: |
| v5.10／v5.16.1 | 0.0860554 | 0.0436875 | 0.0741413 |
| v5.16.2 | 0.0869043 | 0.0320254 | 0.0807882 |
| v5.16.3 | 0.0804418 | 0.0320127 | 0.0737975 |

v5.16.3 的這項預測一致性較好，正式分數卻較差；改善輸入 GNSS 的短期預測，未必改善 map／camera 輸出 pose。轉彎模型也仍依賴 gyro、未知 covariance 與外參假設。[實際回饋數據](../outputs/run/track00_test_2611050020/actual_forecast_3299.json) · [預測圖](../outputs/run/track00_test_2611050020/analysis/13_actual_forecast_3299.png)。

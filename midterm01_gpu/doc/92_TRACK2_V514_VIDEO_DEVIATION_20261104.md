## 影片與灰線是哪一種資料

正確來源是 `/home/ricky/2026-11-04 15-06-59.mov`，不是 Downloads 中的舊影片。RViz 標題、console 的 idx／座標／scale 均對應 `track02_full_2611041506`。影片 1280×720、30 fps，總長 9301.77 秒；定位結束落在 **34:40–34:50**，後面的約兩小時掛機段不作偏離分析。有效段先做 2 分鐘概覽，再加密檢查偏離／狀態切換周邊；沒有宣稱逐一看完全部 279,053 個影片影格。

使用者已確認灰線指道路上沿行進方向延伸的兩條平行地圖線。RViz 的灰色 `LiDAR Map` 來自 `/track2/map`，藍灰色 `Registration Submap` 來自同一 XYZ 地圖的局部範圍；唯一發布的軌跡是橘色 `/track2/path`，紅色箭頭是估計 pose。程式沒有另外發布兩條灰色估計軌跡。

灰線可用來觀察估計軌跡是否與附近道路幾何一致，但 map 只取 XYZ，沒有車道標籤；無法由顏色證明它就是評分真值或規定相機必須行駛的中心線。因此本次沒有把橘線硬移到灰線中間，也沒有把螢幕像素距離冒充公尺誤差。

配準目前把地面用於高度、傾斜和尺度，XY／yaw 則主要使用地面以上結構。`MetricRegistration.prepare()` 的 source feature 高度須超過 `max(0.02 raw, 6×地面 MAD)`，map feature 高度須超過 `max(0.10 m, 3×MAD)`。**看得到的平坦道路線不會因為是灰色直線就自動成為車道位置／方向約束。**這也是「畫面有兩條清楚灰線，定位仍可能靠 GNSS 推進」的模型原因。

## 為何綠色也可能偏離灰線方向

地圖更新解的是 `[x, y, yaw]`，還要處理未知重建尺度。街景若主要提供方向相近的路側平面，側向平移與 yaw 會互相代償：遠處點的橫向錯位，可能由「整台車橫移」或「朝向轉了一點」造成。

程式所稱 rank 1，是經當幀 prior covariance 白化、尺度邊際化後，只有一個資訊特徵值達到門檻，因而只融合一個線性組合；不是把 x、y、yaw 三項都獨立確認了。frame 1546 雖顯示綠色，仍只有 rank 1。這說明了為什麼地圖能接受更新，灰線的方向與當前點雲／估計方向仍可能不完全一致。

1450–1546 的估計 yaw 與目前速度方向差最大約 1.846°。這不是相對真值的 yaw 誤差，但它是兩個運動描述不完全一致的診斷。以純幾何例子說明，30 m 遠處的 1° 方向差就對應約 0.52 m 橫向投影；因此畫面遠處線條的錯位會比相機原點的 XY 差看起來大。

此外，v5.14 的 GNSS XY filter 與航向 bias filter 是分開狀態；GNSS 每約 6–8 幀直接更新位置，而 map correction 另外保存。兩者不同時間更新，會出現橘線折一下、再由 map 慢慢修正的樣子。逐幀分解中最大的側向單步包含 frame 1432 的 GNSS 左向 +0.1599 m、frame 2343 的 +0.1833 m；這些不是當幀 map 造成的跳動。

## frame 623 的新問題：低像素殘差沒有驗證運動正確

這段相機原圖是紋理較少的大路口。回退模型用過去高度與地面平面建立道路 3D 點，再用影像追蹤解 PnP（3D 點到 2D 像素的位姿）。其門檻全部通過：

- 80 個地面 tracks、51 個 inliers，比例 63.75%；像素中位殘差 0.551 px。
- PnP 局部資訊矩陣 rank 6，旋轉量也落在 gyro allowance 中。
- 速度量測 4.8777 m/s、既有估計 8.0145 m/s，innovation 為 −3.1368 m/s。
- 正規化 innovation 平方（NIS）為 2.7435，小於 soft 3.841 與 hard 10.828，因此既沒有降權也沒有拒絕。

濾波器把同一筆速度 innovation 透過位置／速度 cross covariance 同時更新位置，直接套用 `ΔXY = (−0.287747, +0.088041) m`。轉成當幀相機方向為前向 **−0.300830 m**、左向 **−0.007152 m**；它抵消原本的前進 prediction，讓相鄰輸出出現約 1.28 cm 的後退。後續速度又被 GNSS 更新拉回，形成局部先落後再追回的軌跡。

v5.14 相對 v5.13 在 frame 626 的差為前向 **−0.4834 m**、左向 **−0.0097 m**。這直接證明「新版本最大的局部差」主要是縱向，不是整段灰線側偏的原因。

當前 filter prior 也不是速度真值；但這筆回退觀測造成的運動不連續是紀錄可重建的事實。低像素殘差與局部 rank 6 無法排除地面模型偏差、追蹤到錯誤物體或平面 PnP 的替代解。原紀錄沒有保存這 51 個內點的像素座標與完整道路 PnP 位姿，**目前不能聲稱已證明是哪一輛車、哪一塊路面或哪個替代解造成。**原圖只能支持「路口模型需查證」的假說，不能補造缺少的內點診斷。

新增回退共嘗試 429 次，實際只融合這 1 次。其餘 242 次缺乏地面 tracks、185 次 PnP outliers、1 次物理 gate 拒絕。前一區間 frame 616 曾提出 217.6 m/s 並被拒絕；這也顯示此場景的道路模型不是穩定速度來源。

## 能解釋到什麼程度、接下來先修什麼

本次能確認的是輸出被哪些更新推動，以及 v5.14 新增路徑在何處造成明顯運動不一致。不能把 0.01004 的分數差完整分配給 frame 623：官方 Public 使用長度未知的前 5–40% prefix，沒有公開逐幀真值，也不知道 frame 623 是否在實際評分子段。後半段的灰線偏離，更不能直接拿來解釋前段 Public Score。

優先問題是道路回退觀測的運動／幾何一致性及其未校準 covariance，而非把歷史 pose 改得更平順。第二個問題是地圖側向與 yaw 的退化、以及 GNSS 位置更新和 map correction 的互動。後續實作應保留候選內點位置、相對位姿與獨立支持診斷，對因果的真實量測機制做針對性驗證；不把路線強制貼到灰線，也不從榜分反推真值。本次未修改算法或啟動新的 full。
